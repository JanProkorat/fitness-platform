# Rules: i18n

## i18n is a mechanism, not a fixed list

This pack does not name which locales a repo supports — that's a project
fact, declared in the repo's own `CLAUDE.md` (or its i18n library's config:
`i18next`'s `supportedLngs`, etc.). Read that before touching any
user-facing copy. Whatever the list is, "all locales" below means exactly
that list — never a fixed set this pack hardcodes, and never just the one
locale you happen to be testing the device/simulator in.

## When new copy lands

Any new user-facing string MUST land in **every locale file the repo
supports**, in the same change:

- Commonly `src/i18n/locales/<locale>.json` per locale, or a single
  namespaced resource file per feature — match whatever structure already
  exists.

Missing a key in any supported locale is a review-blocking finding. Don't
ship a screen with translations for only the locale you tested in.

## Source of truth

The repo's own config or `CLAUDE.md` names the primary/source locale (the
one product copy is written in first, and the one a missing-translation
fallback should visibly flag rather than silently mimic). If you don't know
a target-locale translation, copy the source-locale string verbatim into
that locale's file and flag the gap explicitly in the PR description —
never leave a key entirely absent (that surfaces as a raw key string or a
broken interpolation in the UI, which is worse than a same-language
placeholder).

## What counts as "user-facing copy"

- Screen/tab titles, button labels, header titles set via
  `<Stack.Screen options={{ title: ... }} />`.
- Error toasts, success toasts, empty-state strings, permission-request
  prompts (camera, notifications, location).
- Validation error messages surfaced to the UI.
- Push-notification title/body, when those are template strings owned by
  this codebase (not hard-coded content generated server-side elsewhere).

## What does NOT need i18n

- Console/log messages (developer-facing).
- Internal API field names, query keys, style-sheet key names.
- Test fixture strings.
- Code comments.

## Every string goes through the i18n mechanism

No bare string literals in JSX for anything a user reads. Use whatever hook
the repo's i18n library provides (`useTranslation()` for i18next, or the
repo's own equivalent) — never hardcode one language directly in a
component and plan to "translate later."

```tsx
// NO
<AppText>Save</AppText>

// YES
<AppText>{t('common.save')}</AppText>
```
