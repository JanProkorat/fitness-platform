# Rules: i18n

Universal across web + mobile UI work.

## Supported languages

- `cs` — Czech (primary).
- `en` — English.
- `de` — German.

## When new copy lands

Any new user-facing string MUST land in **all three locale files** in
the same PR:

- Web: `web/src/i18n/locales/{cs,en,de}.json`.
- Mobile: `mobile/src/i18n/locales/{cs,en,de}.json`.

Missing a key in any of the three is a `qa-tester` AC failure
(`i18n_check: "fail"` in the handoff schema). Don't ship without all
three populated.

## Source of truth

`cs` is the primary — write it first, then translate. If you write `en`
first, that's fine, but Czech is the language users see by default.

## What counts as "user-facing copy"

- Button labels, page titles, screen titles, tab labels.
- Error toasts, success toasts, empty-state strings.
- Validation error messages from FluentValidation / Zod (when surfaced
  to the UI).
- Push-notification body / title.
- Email-template subject / body (if those are template strings, not
  hard-coded HTML in backend).

## What does NOT need i18n

- Console / log messages (developer-facing).
- Internal API field names.
- Test fixture strings.
- Code comments.
