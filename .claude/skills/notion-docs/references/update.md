# Update mode

The post-task workflow. Runs at the end of every completed task that
touched code, prototypes, or conventions. Directly replaces the old
`progress-update` skill.

## When this runs

Invoke at the end of a task when:
- Code changed under `/backend`, `/web`, `/mobile`, or
- Prototype source or build config changed under `docs/prototypes/`, or
- Project rules / skills changed under `.claude/`, or
- A new convention the docs already mention was altered.

**Do not invoke** for:
- Purely conversational turns (no file changes).
- Mid-task checkpoints — wait until the task is finished.
- Hotfixes that will be reverted immediately.
- Changes that only touch ignored files (lockfiles regenerated without
  semantic change, autogenerated `generated.ts`, build artefacts, etc.).

Sub-agents should **not** each invoke `update` mode. The orchestrator
invokes it once, at the end, aggregating what changed across packages.
This mirrors the old `progress-update` rule and keeps the Changelog
coherent.

## Inputs

Before starting, gather:
1. **Task summary** — what the user asked for, in one sentence.
2. **Changed paths** — `git status --porcelain` + staged files. The set of
   files the task touched is the input to routing.
3. **Today's date** in `YYYY-MM-DD` form (from `<env>` or
   `date +%Y-%m-%d`). Never use relative phrases.

## Steps

### 1. Locate the root page

Run `Notion:notion-search` for the root title. If it doesn't exist, stop
and tell the user to run bootstrap — don't silently create it.

### 2. Route each changed path to a Notion page

Apply the rules in [`routing.md`](routing.md). Every changed path maps to
**zero or one** Notion page:
- Some paths don't need page updates (tests, generated files,
  whitespace-only changes). Collect them only for the Changelog entry.
- Some paths map to a hub page (e.g. a new component category that
  didn't exist). Note that the hub list needs a new line.
- Most paths map to a concrete leaf page (a feature, an entity, a
  screen). Collect the union of these pages.

Produce two lists:
- `pages_to_patch` — leaf pages whose body content genuinely changed
  (new endpoint added, field added to entity, screen behavior changed).
- `pages_to_create` — leaf pages that don't exist yet because the task
  added a whole new feature / entity / screen.

### 3. Patch existing pages

For each page in `pages_to_patch`:
1. Fetch the page with `Notion:notion-fetch` to get its current blocks
   and `page_id`.
2. Find the relevant section by heading. Canonical sections per template
   type are defined in [`page-templates.md`](page-templates.md):
   - Feature page: `Endpoints`
   - Entity/Document page: `Fields`, `Relationships`
   - Screen/Page: `State`, `Behavior`
3. Rewrite just the section body — don't touch unrelated sections. This
   is surgical, not wholesale replacement.
4. Append a bullet to the page's `## Recent changes` footer section:
   ```
   - YYYY-MM-DD — <one-line summary>. <link to Changelog entry>
   ```
   Keep this section bounded — if it exceeds ~10 bullets, trim the
   oldest so it stays readable. The Changelog page holds the full
   history.

### 4. Create new leaf pages

For each page in `pages_to_create`:
1. Search first to rule out duplicates (e.g. a sibling page with similar
   title already exists).
2. Create under the correct hub parent with the matching template from
   [`page-templates.md`](page-templates.md).
3. Update the hub page's list to include the new sub-page link.

### 5. Append the Changelog entry

The Changelog entry format mirrors the old `docs/PROGRESS.md` exactly —
trainers and the orchestrator know how to read it:

```
## YYYY-MM-DD — <one-line summary of the task>

### <Package> (`<path>`)

**Added / Modified / Removed: `<relative/path>`:**
- Concrete bullets, git-blame-able.
- Why, when not obvious.
```

Rules:
- Append at the **top** of the Changelog page body, directly under the
  intro paragraph. Newest first.
- **One entry per task.** Don't merge unrelated tasks. Don't split one
  task. If two sub-agents produced changes, the orchestrator combines
  them into one entry.
- Before appending, read the current top entry. If its date + summary
  match what you're about to write, you've already recorded this task —
  stop, don't duplicate.
- Use `**Added:**` / `**Modified:**` / `**Removed:**` labels to group
  bullets per file.
- Package sub-headings: `### Backend (/backend)`,
  `### Web (/web)`, `### Mobile (/mobile)`,
  `### Repo root (.claude/)`. Only include those the task touched.
- Link page references as Notion mentions where possible (e.g. mention
  the Feature page the task updated). Fall back to repo-relative code
  paths in `` inline code `` when a Notion page doesn't exist.

### 6. Report back

Return a concise summary to the orchestrator:
- Changelog entry written? ✅/❌
- Pages updated: list with URLs.
- Pages created: list with URLs.
- Anything skipped (and why).

## Example

Task: "add ArchivePlan endpoint to the backend"

Routed pages (from `routing.md`):
- `/backend/.../Features/NutritionPlans/ArchivePlan/*.cs` →
  `Backend / Features / Nutrition Plans` (patch)
- `/backend/.../FitnessPlatform.Tests/Endpoints/NutritionPlans/ArchivePlanTests.cs`
  → no page update (tests), only Changelog bullet
- `/backend/.../Domain/Constants/ErrorCodes.cs` →
  `Architecture & Conventions / Auth & roles` (tiny patch) **or** skip
  if it's just a new code constant not worth surfacing

Actions:
1. Patch the Nutrition Plans feature page: append one row to the
   `Endpoints` table — `POST /nutrition/plans/{planId}/archive`,
   role trainer/nutritionist, Mongo `Version` check.
2. Append to that page's `Recent changes`:
   `2026-04-17 — Added archive endpoint. ↗ Changelog entry.`
3. Append the Changelog entry (format in step 5 above).

## Failure modes

- **Path maps to no page and no hub.** Fall back to a Changelog-only
  entry. Note in the report that the path was ungoverned.
- **Page fetch fails.** Don't create a duplicate; stop and surface the
  error. The orchestrator may retry.
- **Changelog page missing.** Bootstrap hasn't run yet, or somebody
  renamed it. Stop and ask.
- **Two update calls for the same task.** The top-of-page duplicate
  check catches this. If the entry is already there, do nothing and
  return `"already recorded"`.
