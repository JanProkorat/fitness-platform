# notion-docs — project documentation in Notion

This skill treats Notion as the project's canonical documentation. It has
**two modes**, and every invocation runs exactly one:

| Mode | When | Reference |
|---|---|---|
| `bootstrap` | First-time setup, or a rebuild requested by the user. | [`references/bootstrap.md`](references/bootstrap.md) |
| `update` | After any completed task that changed code, prototypes, or conventions. | [`references/update.md`](references/update.md) |

Decide the mode before doing anything else:

- If the user says "bootstrap", "build the docs from scratch", "start the
  documentation", OR a search for the root page in Notion returns nothing →
  **bootstrap**.
- Otherwise (task just finished, small change, "update the docs") → **update**.

If genuinely ambiguous, ask once with `AskUserQuestion`. Don't guess.

## Notion conventions this skill assumes

- A single **root page** titled `GoodFellas — Fitness & Nutrition Platform`.
  Its Notion page ID is the anchor for everything else. The bootstrap step
  creates it; the update step discovers it via `Notion:notion-search`.
- **Hub-and-sub-pages** layout (not a database). Readable top-to-bottom like
  a wiki. See [`references/page-templates.md`](references/page-templates.md)
  for the canonical tree.
- **Changelog page** lives at `<root>/Changelog` and records every task
  update as a dated H2 section — same format muscle memory as the old
  `docs/PROGRESS.md`, so humans skimming it feel at home.
- **Source of truth is code.** Notion pages are regenerated from code on
  bootstrap and surgically patched on update. Don't hand-edit content the
  skill produced unless you also update the generator rules here.
- **Prototype live previews.** GitHub Pages serves the three built
  prototype artefacts from `develop:/docs` at:

  ```
  https://janprokorat.github.io/fitness-platform/mobile_prototype.html
  https://janprokorat.github.io/fitness-platform/trainer_prototype.html
  https://janprokorat.github.io/fitness-platform/notion_portal.html
  ```

  Each prototype's nav script reads `?scene=<id>` on first load and jumps
  to the matching scene, so URLs like
  `…/trainer_prototype.html?scene=profil` are stable deep-links. Use
  these URLs inside Notion `embed` blocks on Prototype/Web/Mobile pages
  so readers see the live prototype inline — no screenshots, auto-updates
  on every merge. Templates in
  [`references/page-templates.md`](references/page-templates.md) spell
  out where the embed goes.

## Notion tools to use

The Notion MCP server exposes several tools. Use the `Notion:` slash commands
or the direct MCP tools available in the current session:

- **Search:** `Notion:notion-search` (or the `/Notion:search` command)
  — find existing pages by title. Always search before creating to avoid
  duplicates.
- **Fetch:** `Notion:notion-fetch` — read an existing page's content + ID
  before editing, so you append/patch rather than overwrite.
- **Create pages:** `Notion:notion-create-pages` (or `/Notion:create-page`)
  — create one or many pages under a parent `page_id`. Use the multi-page
  form when scaffolding a whole sub-tree in one call; it's much cheaper
  than a loop.
- **Update / append blocks:** whatever the running session exposes for
  editing Notion page content. If the tool surface has changed, prefer
  append-style updates (new blocks at the end) over full-page rewrites
  unless the content being replaced was machine-generated by an earlier
  run of this skill.

If a tool is missing, stop and tell the user rather than faking it. Do not
write half-updated state.

## Golden rules

1. **Search before create.** Never create a page without first searching
   for its exact title under the expected parent. Duplicates in Notion are
   painful to merge.
2. **Idempotence.** Running `bootstrap` twice on the same root must not
   produce duplicate pages. Running `update` twice for the same task must
   not produce duplicate Changelog entries — check the top Changelog entry
   before appending.
3. **One Changelog entry per completed task.** Same rule as the old
   PROGRESS.md: don't merge unrelated tasks, don't split one task across
   entries. Use today's date in `YYYY-MM-DD` form from the `<env>` block or
   `date +%Y-%m-%d`.
4. **Page-scoped content.** Keep the top of each topical page stable
   (overview, fields, routes). Put running "Recent changes" notes in a
   dedicated sub-section at the bottom, so the main content doesn't churn
   every task.
5. **Absolute links.** When referencing code, use repo-relative paths in
   inline code (e.g. `` `backend/FitnessPlatform.Application/Features/Foods/` ``).
   Do not link to local file URLs.
6. **Cost awareness.** Bootstrap touches a lot of pages. Fetch source files
   only as needed; batch page creates; do not re-list every field of every
   entity in the skill — the generator rules live in
   [`references/page-templates.md`](references/page-templates.md) and
   describe the *shape*, not literal copy-paste content.
7. **No PROGRESS.md writes.** This skill replaces `progress-update`.
   `docs/PROGRESS.md` is frozen history; do not append to it. If a sub-agent
   tries to, stop and surface that to the user.

## Workflow at a glance

```
User / orchestrator invokes this skill
          │
          ▼
   Decide: bootstrap or update?
          │
   ┌──────┴──────┐
   ▼             ▼
bootstrap     update
   │             │
   │             ├─ Determine affected pages via routing.md
   │             ├─ Fetch each page, patch the relevant section
   │             └─ Append dated entry to Changelog page
   │
   ├─ Search for / create the root page
   ├─ Scaffold the full tree in one create-pages call
   ├─ Fill each page from code via page-templates.md
   └─ Create an empty Changelog page (no entries yet)
          │
          ▼
   Report back: list of pages touched + link to root
```

## Related skills to chain

- `engineering:documentation` — if a cross-package architecture concept was
  added (new aggregate, new auth boundary, new RT event category), consider
  whether a top-level `Architecture` sub-page needs a deeper writeup, not
  just a Changelog bullet.
- `engineering:standup` — for daily / weekly summaries, operate over the
  Changelog page rather than re-deriving work from git.
- `prototype-scene` — when a prototype is edited, this skill should update
  the corresponding Prototypes sub-page too; `prototype-scene` edits the
  HTML, `notion-docs` reflects it in Notion.

## Checklist (copy into task list on invocation)

- [ ] Decided mode (`bootstrap` or `update`) and announced it.
- [ ] Located the root page (by search or by creating it in bootstrap).
- [ ] If `update`: identified the specific pages to patch via `routing.md`.
- [ ] Ran a `Notion:notion-search` before any create, to avoid duplicates.
- [ ] Appended a single dated Changelog entry (update mode only).
- [ ] Reported back the list of Notion pages created or modified, with URLs.
- [ ] Did **not** touch `docs/PROGRESS.md` or the deprecated
      `progress-update` skill.
